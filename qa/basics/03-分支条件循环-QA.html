分支、条件与循环 Q&A#

章节定位：第 3 章（模块一）· 对应用户指南 user_guide/basics/flow.rst

通用排错方法论见 00-通用排错指南——尤其要先读它的 0.3 顶层异常层级树：本章绝大多数报错都挂在那棵树的 SyntaxError → IndentationError → TabError 这一串（语法/缩进家族）以及 ValueError、IndexError、KeyboardInterrupt 几个分支上。

实测声明：本文每一条报错均在本机真实运行验证、Traceback 原文照录；两条「死循环」现象用后台线程模拟用户按 Ctrl+C 触发真实 KeyboardInterrupt 复现。

对齐说明：条目标题与正文小节对应，报错角度覆盖正文 + 配套 PPT 中的典型易错点。

3.1 分支与缩进基础#

气象类比一句话：缩进和冒号就是 Python 的「分界线上的红绿灯」。真实气象分布图上，冷暖气团的分界面用一条等值线就能标清；而 Python 里「哪几行属于某个 if 分支」完全靠缩进划分。红绿灯没立起来（忘了 :）、或者白线画歪（缩进错乱），整片天气系统就崩了。

3.1.1 忘写冒号 —— SyntaxError: expected ':'#

现象 / 真实报错信息（CPython 3.12）

temp = 32
if temp > 30
    print("今天最高气温超过 30℃，高温日")

  File "...\sim\ch03\s1_missing_colon.py", line 4
    if temp > 30
                ^
SyntaxError: expected ':'

注意：报错的光标（``^``）点在 ``if temp > 30`` 那一行末尾，而报错行号往往标的是「``if`` 的下一行」（这里是 line 4，即缩进的 print 那行）。因为解释器要等读到下一行才知道你漏了冒号。

原因：Python 中每个复合语句（if / elif / else / for / while / def / class…）的条件/表头后面必须跟一个冒号 ``:``，它宣告「下面缩进的代码块属于我」。漏掉它，解释器在这个位置期望读到 :（在 3.12 里直接提示 expected ':'）。

解决办法：在括号（条件）末尾补上冒号，一个都不要少：

temp = 32
if temp > 30:
    print("今天最高气温超过 30℃，高温日")   # 输出：今天最高气温超过 30℃，高温日

进阶提示：有的 Python 环境里同样错误显示成 SyntaxError: invalid syntax，其实是同一件事，不必惊慌——都是「漏了冒号」或「冒号写成了别的字」。搜 python if missing colon 即可看到大量同类案例。

气象场景一句话：给兰州站做「≥35 ℃ 高温预警」，if temp >= 35 后面少写这个冒号，整个判断直接垮掉——像雷暴预警短信把分隔符发错了一样，信号根本发不出去。

3.1.2 分支/循环体忘缩进 —— IndentationError: expected an indented block#

现象 / 真实报错信息

if True:
print("这是 if 分支体内的语句，但没缩进")

  File "...\sim\ch03\s2_missing_indent.py", line 3
    print("这是 if 分支体内的语句，但没缩进")
    ^^^^^
IndentationError: expected an indented block after 'if' statement on line 2

原因：if ...: 后面必须换行 + 至少缩进一层（一个代码块）才构成一个合法分支。Python 规定「一个块起始符后面必须紧跟一条（缩进的）语句」，不能留空或顶格下去。这是第 3 章、也是全 Python 第一高频报错——很多同学抄别人的 if 时忘了把分支内的句子向右推。

解决办法：把属于该分支体的每一行，统一向右缩进 4 个空格：

if True:
    print("这是 if 分支体内的语句，没缩进才是错的")   # 输出：这是 if 分支体内的语句，没缩进才是错的

最容易犯的两个变体：① 从网上复制代码时缩进被啃掉；② 中文输入法状态下打出全角空格（把全角空格清掉重敲空格）。全角空格是“隐形杀手”，编辑器里看着一样，实则是非法字符。

气象场景一句话：气温等级判定的 if / elif / else 里只要有一处忘了缩进，那一行就掉出分支——等于“暴雨等级漏判一级”，雨量 30 mm 明明该是暴雨，却因为没缩进被当普通代码执行，结果全错。

3.1.3 多了不该有的缩进 —— IndentationError: unexpected indent#

现象 / 真实报错信息

print("开始")
    print("这一行被不小心多缩进了，正常应该是顶格")

  File "...\sim\ch03\s3_unexpected_indent.py", line 3
    print("这一行被不小心多缩进了，正常应该是顶格")
IndentationError: unexpected indent

原因：Python 没有大/中括号划分块，顶层层级（模块层）的代码一旦莫名向左推进了几个空格，Python 就不知它属于哪个块，直接报「意外的缩进」。通常是：print 顶格语句被多敲了空格、或整段代码无意中整体被 Tab/空格推入。

解决办法：确认这一行不属于任何分支时把它退到最左侧（顶格）；属于某个块时，退到与同类兄弟语句完全一致的列。

print("开始")
print("这一行顶格，输出正常")

排查小窍门：打开代码编辑器的「显示空白字符 / 渲染空白」（VS Code Ctrl+P 输入 Toggle Render Whitespace），空格会显示成小圆点 ·、Tab 显示成 →，一眼看清每行到底缩进了几格。凡缩进不一致，先用编辑器「格式化文档」（VS Code Shift+Alt+F）一键排齐。

气象场景一句话：多一层缩进，Python 就以为这一行属于「另一个更深的天气系统」，等值线嵌套了不该有的内圈——判断结果彻底对不上号。

3.1.4 Tab 与空格混用 —— TabError: inconsistent use of tabs and spaces in indentation#

现象 / 真实报错信息

if True:
\tprint("这一行用了 Tab(8 列)")
    print("这一行用了 4 个空格")

  File "...\sim\ch03\s4b_tab_error.py", line 4
    print("这一行用了 Tab(8 列)")
TabError: inconsistent use of tabs and spaces in indentation

说明：上面代码第一行分支体用的是真实 Tab 字符、第二行用 4 个空格，同一个块用两种字符，Python 认为缩进「无法唯一判定层级」，抛 TabError。这是 IndentationError 的特例——在 0.3 层级树里，TabError 是 IndentationError 的子孙。（通常第一步跑出来的可能是 IndentationError: unindent does not match...，报的是同一类病。）

原因：Tab 和空格混用导致缩进「同一列却可由多种字符组合得到」，Python 无法确定该行属于哪一层，拒绝运行。

解决办法：统一、统一、再统一——只用 4 个空格，永远不按 Tab 缩进。把编辑器 Tab 键改成「插入 4 个空格」：

  • VS Code：左下设置 → 搜 insert spaces → 勾选，并设 Tab Size = 4；再开启 Render Whitespace 看清晰是我空格。

  • PyCharm：File → Settings → Editor → Code Style → Python，勾选 “Use tab character: off”、Indent 填 4。

  • Jupyter / 终端里误按了 Tab，把这一行整行退格重敲 4 空格。

老文件已经混了怎么办？用编辑器「全选 → 把 Tab 转成空格」（VS Code Ctrl+Shift+P → “Convert Indentation to Spaces”）一键清洗。

气象场景一句话：同一片观测场，一个站点用格点数据、一个用站点数据、单位还不统一——数据根本没法放一起算。Tab/空格混用就是代码里的「单位不统一」，Python 直接拒绝开工。

3.1.5 空代码块：if x: 下只写了注释 —— 也要 IndentationError，用 pass 占位#

现象 / 真实报错信息

rain = 12.5
if rain > 10:
    # 这里还什么都没写，先留个待办
print("打印这一行本该在 if 外，但它其实想进分支")

  File "...\sim\ch03\s10_empty_block.py", line 5
    print("打印这一行本该在 if 外，但它其实想进分支")
    ^^^^^
IndentationError: expected an indented block after 'if' statement on line 3

原因：注释不算语句。if ...: 后面的块里如果只写了 # 注释、没有任何可执行语句，这个块还是「空的」，Python 照样要求你一定给一条语句。很多同学以为「写了注释就等于填满了块」，结果注释底下的 print 又没缩进，于是 if 的分支空心、代码块缺失。

解决办法：方案一，把想放进分支的语句真正缩进进去；方案二，暂时还没想好写什么时，用``pass`` 占位（pass 是一条“什么都不做的合法语句”）：

rain = 12.5
if rain > 10:
    # 这里还什么都没写，先留个待办
    pass          # 占位：这个分支将来会写预报结论
print("这一行顶格，正常执行")

pass 用于 Python 语法要求“必须有语句”但你暂时不想写任何逻辑的空块；...（省略号字面量）也常被拿来占位，但建议初学者统一用 pass，语义更直白。

气象场景一句话：「降水等级≥暴雨」预警的分支，你只写了句「待补充」注释就想收工——Python 不认，它只认实打实的预报动作；先把架子搭好用 pass 占位，改天再填阈值逻辑。

3.2 条件判断与逻辑运算#

3.2.1 条件里误写赋值 =（应当 ==）—— SyntaxError#

现象 / 真实报错信息

x = 5
if x = 5:
    print("x 等于 5")

  File "...\sim\ch03\s5_assign_in_cond.py", line 3
    if x = 5:
       ^^^^^
SyntaxError: invalid syntax. Maybe you meant '==' or ':=' instead of '='?

原因：if 的条件里必须是「产生 ``True/False`` 的表达式」，而 = 是赋值语句、不是比较。把 x = 5 塞进 if 会让解释器在条件位置读到一条赋值，语义非法。这一条在 flow.rst 里有专门 warning：「单独的 = 仅表示赋值，判断相等必须用 ==」——正是第一高频报错。3.12 版本甚至贴心地提示你「Maybe you meant == or :=」。

解决办法：判断相等用双等号 ``==``：

x = 5
if x == 5:
    print("x 等于 5")   # 输出：x 等于 5

延伸：如果确实想在条件里「一边赋值一边判断」，那是 Python 3.8+ 的海象运算符 := 的活（if (m := 后台读取到的值) > 0:），本章不必掌握，但看到报错里提示 := 就知道它说的不是你现在要的。

气象场景一句话：判断「今天是否达高温」却写成 if temp = 35，等于把「天气」当「命令」使唤——不是查天气，而是把温度硬改成 35，Python 当然拦下你（语法错误），气象等级判定瞬间失守。

3.2.2 if/elif/else 结构错误：elif 单独出现、else 后跟条件 —— SyntaxError#

三类真实报错信息

# ① elif 前面没有 if（elif 不能打头）
score = 85
elif score >= 60:
    print("及格")

  File "...\s6_elif_alone.py", line 3
    elif score >= 60:
    ^^^^
SyntaxError: invalid syntax

# ② else 后面不能跟条件(else 只兜底)
temp = 32
if temp > 30:
    print("高温")
else temp > 20:
    print("偏热")

  File "...\s7_else_with_cond.py", line 5
    else temp > 20:
         ^^^^
SyntaxError: expected ':'

# ③ else 单独出现、前面既没有 if 也没有循环
x = 10
else:
    print("else 无处安放")

  File "...\r7_else_alone.py", line 3
    else:
    ^^^^
SyntaxError: invalid syntax

原因：elif 和 else 都必须依附在某个 ``if`` 之后，它们是「接续器」不是「开头」。else 关键词后面不接任何条件（它兜底其余所有情况）——这是 flow.rst 三件必记之一。三个反模式分别犯：elif 打头、else 带条件、else 孤立。

解决办法：理清层级，elif 前面必有 if，else: 后面直接换行写块、绝不给它写条件：

rain = 45.0
if rain < 10:
    print("小雨")
elif rain < 50:     # elif 在 if 之后，条件照写
    print("大雨")
else:               # else 不接任何条件
    print("暴雨及以上")

判定顺序提醒（PPT 第 14 页专门强调）：``elif`` 自上而下，条件有包含关系时先小后大。if score>=60: D / elif score>=70: C / elif score>=80: B / elif score>=90: A 这组是反的——它会先判 60，一切到底，90 分永远进不了 A。正确顺序是从大往小（>=90 在前）或像视频里那样用「阶梯式单边比较」。

气象场景一句话：降水等级判定，elif 使劲往前凑却搭不上 if，或 else 后面还拖着个条件——等于预警分级表上的「箭头」画错了方向，本应「无雨→暴雨」的阶梯从此断档，漏级在所难免。

3.2.3 条件判断的 Truthiness：空列表 / None / 0 的布尔值，避免 if 列表 == True#

现象 / 真实输出（无报错，但判断结果颠覆直觉）

empty_list = []
if empty_list == True:
    print("empty_list 是 True")
else:
    print("empty_list == True 是 False，这个 if 是错的")
print("直接 if empty_list：", "非空" if empty_list else "空")

bool([])      = False
bool(None)    = False
bool(0)       = False
bool(1)       = True
empty_list == True 是 False，这个 if 是错的
直接 if empty_list： 空

原因：在条件判断里，Python 会对很多值隐式求布尔值（Truthiness）：False、0、0.0、空字符串 ""、空列表 []、空元组 ()、空字典 {}、空集合 set()、None、float('nan') 之外的绝大多数值都是「真」的。而「空列表 ``[]`` 本身不等于 ``True``」——[] == True 永远是 False（== 是比较数值相等，0 == True 都不成立，[] 更不成立）。所以判断集合是否非空，正确写法是直接 ``if 列表:``，别拿它和 True 比。

解决办法：想判断「某站有没有数据」时，直接测集合本身的真假：

stations = ["兰州"]
if stations:                       # 非空 → 真
    print(f"有 {len(stations)} 个站点")
else:
    print("没有站点数据，需补充观测")

记忆口诀：审值时，``0/空/None/False`` 都是假，其余基本是真。判断「非空」写 if 列表:(读作“如果有东西”)，判断「是空」写 if not 列表:。

气象场景一句话：一群站点的雨量桶都记的是 0.0 mm（空雨量、全空列表），你想知道「到底有没有雨量桶待读取」——写 if 桶清单 == True 会把“啥都没有”误判成“有数据”，把空表格当成满表格去发布，贻笑大方。

3.2.4 链式比较 20 < t < 35 vs and —— 两种等价写法#

现象 / 真实输出（不是报错，是常见困惑——到底该写哪种）

t = 28
print("链式 20 < t < 35:", 20 < t < 35)              # True
print("and   20 < t and t < 35:", 20 < t and t < 35)  # True
t2 = 40
print("链式 t2=40:", 20 < t2 < 35, " and 写法:", 20 < t2 and t2 < 35)

链式 20 < t < 35: True
and   20 < t and t < 35: True
链式 t2=40: False  and 写法: False

（两条写法对任何输入的结果完全一致，选读数更顺眼的即可。）

原因：Python 支持数学意义上的链式比较 a < x < b，它自动展开为「a < x 且 x < b」。这正是 flow.rst 强调的反模式「碎片区间」要避免的东西——但它本身语法合法、逻辑准确，永远等价于 a < x and x < b。注意别把它和 ``and`` 弄混成 ``a < x < b`` 就是 ``and``——其实等价，只是写法不同；真正要警惕的是「链式比较里夹了副作用/变了变量」。

解决办法：两种皆可，随你顺手。推荐：

  • 清晰的范围判定：直接用单条链式 if 20 <= t <= 35:，读数最像数学式；

  • 跨类型的复合条件（如「温度高 或 湿度大」）用 and / or 组合。

t = 28
print("20 <= t <= 35:", 20 <= t <= 35)      # True，推荐的范围写法

易错点提示：别把 ``and`` 当数学连接符连着变量乱写，例如 if t > 20 and < 35: 是语法错误——< 左边缺了操作数，and 前后必须是两个完整的表达式。

气象场景一句话：判断「≤35 ℃ 且 ≥20 ℃ 的适宜温区」写成 20 < t < 35，句子跟气象条件一样“区间明确”；要是东拼西凑漏一半（and < 35），就预告片缺了半截，判定范围直接破洞。

3.2.5 or / and 的短路返回值：返回「表达式」，不是布尔#

现象 / 真实输出

def sensor(): print("调用 sensor()，返回缺测 None"); return None
def backup(): print("调用 backup()，返回备用值 25.0"); return 25.0
result = sensor() or backup()     # 主传感器缺测(None→假)，or 会去取备用
print("or 的结果是:", result)
print(0 or "默认值")
print(28 or 0)
print(28 and 0)

调用 sensor()，返回缺测 None
调用 backup()，返回备用值 25.0
or 的结果是: 25.0
默认值
28
0

原因：x or y 的逻辑是「若 x 为真，返回 x；否则返回 y」；x and y 则是「若 x 为假，返回 x；否则返回 y」。所以它返回的是参与运算的某个值本身，不一定是 True/False。这就是「取缺测时的备用值」的经典写法——sensor() or backup() 在 sensor() 拿到 None（假）时自动落回 backup()。

解决办法：

  • 想要真的布尔结果，用 bool(...) 包一下：print(bool(0 or "默认值")) 是 True；

  • 想实现「取备胎」逻辑，A or B 正是你要的，别绕路写 if A: use A else: use B；

  • 想判断「A 和 B 都得是真」再用 A and B 当条件。

station_temp = None                # 某站缺测
backup_temp  = 25.0
t = station_temp if station_temp is not None else backup_temp   # 显式取备
print("最终采用温度:", t)              # 25.0

拓展提醒：短路(short-circuit)意味着 or / and 可能不执行第二个表达式——上面 backup() 只在 sensor() 为假时才被调用。别依赖“两个函数都被调用”去收数据。

气象场景一句话：主站观测仪坏了返回 None，你想「主站不行就自动用备用站」——主站气温 or 备用站气温 一个式子就搞定；这正是把 or 的短路当“多传感器自愈”用的贴合场景。

3.3 for 循环#

气象类比一句话：for 就像让探空气球逐层爬升、挨层读温度，每一层是列表里的一个元素；把探测器装错要用“新列表”而不动原列表，才不会被上一次气球挤压带乱次序。

3.3.1 遍历列表时修改正在迭代的列表 —— 跳过元素 / 错位 / 可能报错#

现象 / 真实输出（无报错，但结果错！——最阴险的一类）

temps = [25, 32, 28, 35, 30, 27]
for t in temps:
    if t >= 30:          # 想删掉所有"高温日"(>=30)
        temps.remove(t)  # 边遍历边删 → 索引错位
    print("  当次取到", t, "，当前列表", temps)
print("删除后:", temps)

删除前: [25, 32, 28, 35, 30, 27]
  当次取到 25 ，当前列表 [25, 32, 28, 35, 30, 27]
  当次取到 32 ，当前列表 [25, 28, 35, 30, 27]
  当次取到 35 ，当前列表 [25, 28, 30, 27]
  当次取到 27 ，当前列表 [25, 28, 30, 27]
删除后: [25, 28, 30, 27] （35 没被删掉 = 被跳过了！）

原因：for 内部用一个游标，每轮移动一次去找下个元素。你在取到 32 时把它 remove 掉了，后面的 28 顺势前移一位、被游标跳过；同理 30 跳掉。结果 35、30 两个高温日明明 ≥30 却没被删——边遍历边改列表，游标和长度错位。若在循环里 append 增加元素，还可能造成列表无限变长、循环转不完；若一边删又把列表删空/越界，还会顺手触发 IndexError。

解决办法：不要边遍历边改原列表。三种安全做法（推荐第一种）：

  • 遍历它的副本 for t in temps[:]:（切片产生新列表，删原列表互不干扰）；

  • 用列表推导式新建 kept = [t for t in temps if t < 30]；

  • 从后往前删（for i in range(len(temps)-1, -1, -1):），因为删末尾不影响前面游标。

temps = [25, 32, 28, 35, 30, 27]
kept = [t for t in temps if t < 30]     # 只留非高温(推荐)
print(kept)                              # [25, 28, 27]

flow.rst 的列表推导式正是为这个场景准备的：high_days = [t for t in temps if t>=35] 一步筛出、不动原列表。

气象场景一句话：你想从逐日气温里「剔除 ≥35 ℃ 的高温日」，却边扫边删原数组——像探针在改自己的采样路径，有的高温日被“卡位跳过”，最后说你没发现有高温，实际天天 38 ℃。

3.3.2 用 range(len(x)+1) 取下标，越界 —— IndexError: list index out of range#

现象 / 真实报错信息

names = ["兰州", "北京", "上海"]
for i in range(len(names) + 1):   # 多跑一次 → i=3 越界
    print(i, names[i])

0 兰州
1 北京
2 上海
Traceback (most recent call last):
  File "...\sim\ch03\r4_index_error.py", line 4, in <module>
    print(i, names[i])
             ~~~~~^^^
IndexError: list index out of range

原因：列表下标从 0 开始，有效范围为 0 .. len-1。range(len(names)+1) 会生成到 len 本身（这里是 3），而 names[3] 不存在——Off-by-one（差一）错误。flow.rst 里给了用 range(len()) 配合下标的写法，稍不留神多 +1 就越界。

解决办法：改成 range(len(names))，或更好用 enumerate 同时拿下标和值（见 §3.3.3）：

names = ["兰州", "北京", "上海"]
for i, city in enumerate(names):     # i 自动从 0 到 2
    print(i, city)

深究：IndexError 是 LookupError 的子孙（0.3 层级树），跟第 2 章“索引”主题同源；本章只是它出现在 for + len 组合里。看到它先数一遍 len 与循环到底跑几次。

气象场景一句话：遍历 30 天资料却写了 range(len(t)+1)——探空气球多爬了一层拿云端空气当下层，第31天 根本不存在，IndexError 拦下你这颗“不该升的空球”。

3.3.3 枚举/解包个数不匹配 —— ValueError: not enough / too many values to unpack#

现象 / 真实报错信息（两个方向都演示）

data = [("兰州", 28.1), ("北京", 29.4)]
for station, temp, alt in data:   # 想要 3 个，元组只有 2 个 → not enough
    print(station, temp, alt)

ValueError: not enough values to unpack (expected 3, got 2)

data = [("兰州", 28.1, 1000), ("北京", 29.4)]
for station, temp in data:        # 前面元组有 3 个，只写 2 个变量 → too many
    print(station, temp)

ValueError: too many values to unpack (expected 2)

原因：for a, b in ... 要求每个被迭代元素都能解出 ``a``、``b``。写几个变量就得有几个值：变量比值多 → not enough；值比变量多 → too many。数据里混进“长短不齐”的记录就翻车。flow.rst 用的 for station, temp in zip(...) / weather.items() 都靠这种解包——前提是每个元组长度一致。

解决办法：保证每个元素结构一致；被迭代对象不确定时，先 print 前几项看看长度，或改用更稳妥的写法（每项只取固定下标，不展开）：

# 方案一：保证数据齐整
data = [("兰州", 28.1, 1000), ("北京", 29.4, 500)]
for station, temp, alt in data:
    print(station, temp, alt)

# 方案二：不强行解包，用下标访问，容忍结构不同
data2 = [("兰州", 28.1, 1000), ("北京", 29.4)]
for item in data2:
    station = item[0]
    temp    = item[1]
    print(station, temp)

关联记忆：enumerate 每项返回 (下标, 值) 二元组，所以 for idx, val in enumerate(lst) 的变量个数必须刚好 2 个；多写一个变量也会 not enough values to unpack。

气象场景一句话：站点气温表里，“北京”那行某天少记了个高度字段，for 站,温,压 in 表 一解包就爆 not enough values——像雷达拼图上有一块缺了回波，拼图机当场报警。

3.3.4 for...else 少用却常踩 —— else 是「循环正常跑完」才执行#

现象 / 真实输出（无报错，但和 if 的 else 行为完全不同）

print("== 场景A：没发生 break，else 执行 ==")
temps = [18, 21, 24, 27]
for t in temps:
    if t >= 35:
        break
else:
    print("一个 >=35 的高温都没有，else 正常收尾")

print("== 场景B：发生 break，else 不执行 ==")
temps2 = [18, 38, 42]
for t in temps2:
    if t >= 35:
        print(f"找到超过 35 的 {t}，break 打断")
        break
else:
    print("不该走到这里")

== 场景A：没发生 break，else 执行 ==
一个 >=35 的高温都没有，else 正常收尾
== 场景B：发生 break，else 不执行 ==
找到超过 35 的 38，break 打断

原因：for/while 后接的 else 是「循环没被 ``break`` 打断、自然跑完」才执行一次的奖励块——不是 if 的 else。PPT 第 47 页原话：「当循环没有被 break 语句退出时，执行 else 语句块」。很多人以为它是 if 的兜底，逻辑全反。

解决办法：适合「找东西，找不到就宣布未出现」。示例（flow.rst 的 while-else 找超阈值下标的思想）：

temps = [18, 21, 24, 27, 32, 35]
for t in temps:
    if t >= 35:
        break
else:
    print("整段资料里没有 ≥35 ℃ 的高温")   # 只在没遇到高温时打印

提醒：若 for 里根本没写 break，那 else 永远都会执行——这种写法基本没有意义；else 就是为 break 配套“反向收尾”的。

气象场景一句话：遍历 7 日资料找「会不会出现单日 ≥35 ℃」——break 一找到就撤，没找到则 for...else 的 else 才出来说「本周无高温」；这是“巡逻哨巡完一圈没发现异常才收队”的气象侦察写法。

3.4 while 循环#

气象类比一句话：while 是一步步给温度计加温直到触发阈值的“渐进过程”，条件是那个阈值；只要没人给温度计加热、或加热的方向错了，它就永远在空中转圈——无限循环。

3.4.1 死循环：while 忘了更新条件变量 —— 程序卡住，Ctrl+C（KeyboardInterrupt）#

现象 / 真实报错信息（后台线程 ≈ 用户按 Ctrl+C，完整复现）

import time
temp = 28.0     # 起始气温
hour = 0
while temp < 35:            # 想让温度升到 35，可循环体里没有 temp 的变化
    hour += 1
    print(f"第 {hour} 小时，气温仍是 {temp}℃")
    time.sleep(0.05)
print(f"经过 {hour} 小时，触发高温预警！")    # 永远到不了

第 1 小时，气温仍是 28.0℃
第 2 小时，气温仍是 28.0℃
   ……（程序卡死，这一行会无限刷屏下去）……
第 30 小时，气温仍是 28.0℃
>>> 用户按下 Ctrl+C，触发 KeyboardInterrupt <<<
Traceback (most recent call last):
  File "...\sim\ch03\r5_infinite_while.py", line 17, in <module>
    time.sleep(0.05)
KeyboardInterrupt

原因：while temp < 35 的条件里出现了 temp，但循环体内没有任何一行让 ``temp`` 朝 35 靠近——temp 永远是 28，条件永远为真，while 永不结束。flow.rst 的 warning 原话：「while 循环体内必须更新条件涉及的变量（temp += 0.5），否则条件永远为真，程序卡死。」这是 while 第一大坑。

解决办法：while「三大保命习惯」（flow.rst 原文）——

  1. 循环体内更新条件变量：凡是条件里出现的变量，循环体里至少有一处让它朝终止方向变；

  2. 加安全上限：处理未知数据时用 break 在达到上限时强制退出；

  3. 能用 ``for`` 就用 ``for``：只有「次数未知、只靠条件」才用 while，for 天然不会死循环。

temp = 28.0
hour = 0
while temp < 35:            # 阈值停在 35
    hour += 1
    temp += 0.5              # ← 关键更新：温度一步步逼近 35
print(f"经过 {hour} 小时后达到 {temp}℃，触发高温预警")   # 到 35 正常退出

若已经在跑死循环：在 Jupyter/终端里按 Ctrl+C（键盘中断）即可打断该单元格执行，不必重启内核。KeyboardInterrupt 在 0.3 层级树里是 BaseException 的直系，不属于 Exception——所以 try/except Exception 是抓不住它的。

气象场景一句话：统计“气温从 28 ℃ 起每小时升 0.5 ℃、直到触 35 摄氏度阈值预热多久”——只要你在 while 里漏了 temp += 0.5，温度计永远停在 28 ℃，程序就变成了“永远不会放晴的连续阴雨”，只能 Ctrl+C 手动喊停观测。

3.4.2 死循环：continue 跳过了循环体里「更新计数」的那一行#

现象 / 真实报错信息

t = 36.0          # 第 0 天就是"高温日"
i = 0
while i < 7:      # 想数 7 天的等级统计
    if t >= 35:
        continue  # ← continue 直接跳过了下面 i += 1，i 永远 0
    i += 1
    t += 0.5
print("完成统计")

>>> 用户按下 Ctrl+C <<<
Traceback (most recent call last):
  File "...\sim\ch03\r6_continue_skip_increment.py", line 15, in <module>
    continue  # ← continue 跳过了下面 i += 1，i 永远 0
    ^^^^^^^^
KeyboardInterrupt

原因：continue 会把当前这轮剩余代码全部跳过、直接回到循环开头重新判断条件。如果「更新计数器/条件变量」的那几行正好写在 ``continue`` 之后，一旦触发 continue，计数器就再也不会增加，条件永不改变 → 死循环。flow.rst 强调的 continue 应用场景是「跳过缺测数据继续」，但你的更新语句必须放对位置。

解决办法：在 while + continue 混用时，把条件变量的更新放在 ``continue`` 之前（一进来就更新），或者更新单独写在循环体更靠前的位置：

t = 36.0
i = 0
while i < 7:
    i += 1               # ← 先更新计数器，再判断，绝不被 continue 吃掉
    if t >= 35:
        continue         # 跳过的是"统计"，不是"计数"
    print("统计天数:", i)
print("完成统计")

对比镜像坑：continue 用在 for 里是安全的（for 自己管理游标下标）；只有 while 才需要你亲力维护计数变量——这是 while 与 continue 同框时的专属陷阱。

气象场景一句话：逐日算高温天数的 while 里，if t>=35: continue 直接把 i += 1 跳过——从第一天起计数就冻住了，循环像“只会放晴的天数统计器”一样原地打转，永远完不成报表。

3.5 break / continue / return 的适用范围#

气象类比一句话：``break`` 是“发完这条预警就停发”，``continue`` 是“这一站数据缺失，跳过它继续下一个站”。但它们都只能在循环这个“观测机房”里按，出了机房（循环外）按了无效还报错。

3.5.1 break 写在循环外 —— SyntaxError: 'break' outside loop#

现象 / 真实报错信息

temp = 32
if temp > 30:
    print("高温")
    break

  File "...\sim\ch03\s8_break_outside.py", line 5
    break
    ^^^^^
SyntaxError: 'break' outside loop

原因：break 只能出现在 ``for`` / ``while`` 循环体内，它负责“跳出循环”。放在普通 if（不在任何循环里）、函数体等位置，Python 直接判语法非法。

解决办法：if 里的 break 只有在该 ``if`` 位于某个循环内时才合法；想退出的是 if 分支本身，什么都不用写（if 跑完自动向后走）；想退出当前循环，把 break 放进循环体内：

for temp in [25, 35, 40]:
    if temp >= 35:
        print("触发高温预警", temp)
        break          # 在 for 体内，合法；遇到 35 就停

关联注意：嵌套循环里 break 只跳出最内层那个循环（PPT 第 45 页：「break 仅跳出当前最内层循环」）。想一次跳出多层要额外加标志或用函数的 return（此时需把代码包进 def，见 §3.5.3）。

气象场景一句话：想在“扫描 5 站遇缺测即停”时写 break，却放到了循环外的 if 里——等于在观测机房外拔总闸，Python 不允许，直接报 'break' outside loop。

3.5.2 continue 写在循环外 —— SyntaxError: 'continue' not properly in loop#

现象 / 真实报错信息

temp = 32
if temp > 30:
    continue

  File "...\sim\ch03\s9_continue_outside.py", line 4
    continue
    ^^^^^^^^
SyntaxError: 'continue' not properly in loop

原因：与 break 同理，continue（跳过本轮循环剩余部分）只能在 ``for`` / ``while`` 循环体内。放在循环外的 if 里就报「没待在循环里」。

解决办法：确认 continue 处在某个循环内部；若想“跳过当前 if 里的剩余逻辑再走后面的”,二选一：

  • 把 if ... continue 放进循环里（大量缺测日场景）：见下方正确版；

  • 若并不在循环里、只是想 “这一支不算了”,直接改写 if/else 结构即可，不需要 continue。

raw = [25.5, None, 26.0]
for temp in raw:
    if temp is None:
        continue          # 缺测就跳过，不进统计
    print(f"正常记录 {temp}℃")

flow.rst 的「break vs continue 处理缺测」正是如此：break(遇首个缺测即截断)、continue(缺测是常态、跳过继续)。留意区分二者位置都必须落在循环里。

气象场景一句话：逐小时观测里碰到缺测想 continue 跳过，却把 continue 甩在了 for 循环外面——像“跳过这台坏自动站”的指令发给了一个并不存在的站点，Python 拒绝执行并报 not properly in loop。

3.5.3 return 写在循环里、却不在任何函数内 —— SyntaxError: 'return' outside function（进阶延伸）#

现象 / 真实报错信息

for i in range(5):
    return i   # 顶层没有函数，return 没有返回目标

  File "...\sim\ch03\r8_return_outside.py", line 3
    return i   # 顶层没有函数，return 没有返回目标
    ^^^^^^^^
SyntaxError: 'return' outside function

原因：return 的语义是「结束当前函数并把值交还给调用者」。脚本顶层（或裸循环里）没有“函数”这层容器，return 无处可返，Python 报非法。新手常想在循环里 “取到第一个就退出” 而写 return，其实循环里该用 break。

解决办法：分两种情况——

  • 想要「找到就退出循环」：用 ``break``（见 §3.5.1）；

  • 确实想“返回一个值”：把这段包进 def 函数再 return：

def first_high(temps):
    for t in temps:
        if t >= 35:
            return t        # 找到就返回该气温
    return None             # 一个都没有就返回 None

print(first_high([18, 38, 40]))   # 38
print(first_high([10, 12]))       # None

这门课第 4 章会系统讲函数；本章只要记住：脚本顶层不能 ``return``，要么用 ``break``、要么把代码装进 ``def``。

气象场景一句话：想在逐站扫描里“遇到第一个高温站当场交回结果”——先 def 一个探测函数，让 return 有家可回；不然函数都没建，Python 没法把结果“交给上级台站”。

3.6 range() 的参数问题#

3.6.1 range 步长为 0 —— ValueError: range() arg 3 must not be zero；参数不足 —— TypeError#

现象 / 真实报错信息（两个默认都真跑）

list(range(1, 10, 0))   # 步长(第3参)写成 0 → ValueError

ValueError: range() arg 3 must not be zero

list(range())           # 一个参数都没给 → TypeError

TypeError: range expected at least 1 argument, got 0

原因：range(起始, 结束, 步长) 的步长如果为 0，序列“一步都不走、原地踏步”，永远无法推进——Python 直接拦截并抛 ValueError。而 range 至少要 1 个参数（用法可为一个、两个、三个，PPT 第 32 页），0 个参数触发 TypeError（参数个数不对）。

解决办法：步长给非 0 的整数；参数补足 1~3 个（缺的用默认值：起默认 0、步长默认 1）：

print(list(range(5)))          # [0,1,2,3,4]       一个参数
print(list(range(1, 6)))       # [1,2,3,4,5]       两个参数
print(list(range(1, 8, 2)))    # [1,3,5,7]         三个参数
print(list(range(7, 0, -1)))   # [7,6,5,4,3,2,1]   负步长(倒序)合法

附带区分：两种报错别混——ValueError（range() 步长为 0）是“类型没错、值非法”；TypeError（range 参数不足）是“类型/个数不对”。正好呼应 0.3 层级树的 ValueError vs TypeError 一句话区分。

视角提醒：range 返回的是可迭代对象不是列表，for i in range(7) 直接 print(i) 拿的是数字，别试图 print(range(7)) 想看到数字序列（会打印 range(0, 7)）。要想看内容用 list(range(7))。

气象场景一句话：想按步长 3 小时扫一遍 24 小时资料 range(0, 24, 3)，结果手一抖把步长填成 0——探空仪从 0 时起就跟定在原点不动，Python 一眼看穿 range() arg 3 must not be zero，不让你原地打转。
